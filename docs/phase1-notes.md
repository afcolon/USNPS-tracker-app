# Phase 1 — Park Data + Passport Notes

Spec §7 defines "done" for Phase 1 as: *"All NPS parks loaded from the NPS API; user
can mark visited, sees stamps."*

## Decisions made with you (confirmed via prompts)

| Area | Choice | Why |
|---|---|---|
| Auth | None — single implicit user | Solo/personal app; spec's phase list never mentions auth. One `User` row is seeded by the initial migration; all endpoints operate on "the" user (there's only ever one). Real auth can be layered on later without changing the `Park`/`VisitedPark` schema. |
| Passport UI | Grid view | Simpler than a map for v1, no mapping library needed. Map view can be added later as an alternative, not a replacement. |

## Implementation decisions made without asking (low-stakes, documented for easy tweaking)

- **Alembic initialized now** (deferred from Phase 0 per `phase0-notes.md`, now that there
  are real models). Used the **async template** (`alembic init -t async`) rather than adding
  a second sync DB driver, since the app already commits to async SQLAlchemy + asyncpg.
- **First migration is hand-written, not autogenerated.** `alembic revision --autogenerate`
  needs a live DB to diff against, which isn't available in this sandbox (same Docker
  constraint as Phase 0). For a from-scratch "create everything" migration this is simple
  and safe to write by hand; verified with `alembic upgrade head --sql` (offline mode, no
  DB needed) to confirm the generated SQL is correct. Future migrations that need to diff
  against real data should use `--autogenerate` as normal once Postgres is reachable.
- **Seeded user is a placeholder identity** (`Park Explorer` / `owner@example.com`), not a
  real name/email — deliberately, so a real personal email never lands in git history for
  a repo that may end up public. Update the row directly in Postgres if you want your real
  name/email reflected: `UPDATE users SET name = '...', email = '...' WHERE id = 1;`
- **Ingestion is its own separate `uv` project** (own `pyproject.toml`/venv in `ingestion/`),
  not sharing code with `backend/`. It writes to the same Postgres DB via raw SQL upserts
  (`psycopg`, sync) rather than importing backend's SQLAlchemy models — this matches the
  spec's explicit framing of ingestion as "a different concern, different cadence" (§4.3)
  from the live API, and avoids one project's import path depending on the other's
  directory layout. Trade-off: the `parks` table's columns are defined in two places
  (Alembic migration + the upsert SQL); if they drift, the upsert will fail loudly (unknown
  column), which is an acceptable failure mode at this scale. `ingestion/.env` uses a plain
  `postgresql://` URL (sync `psycopg`) — note this differs from `backend/.env`'s
  `postgresql+asyncpg://` for the *same* database.
- **Designation filter, verified against the real API (2026-09-16):** filtering on
  `"National Park" in designation` alone gave **60**, not 63. Three real-world quirks
  needed fixing, confirmed against a live NPS API key:
  - **`npsa` (American Samoa)** — NPS leaves `designation` blank for this one. Special-cased
    by park code (`MANUAL_INCLUDE_PARK_CODES` in `load_parks.py`) rather than trusting
    `designation`.
  - **`redw` (Redwood)** — officially *"Redwood National and State Parks"*; the word order
    means the substring `"National Park"` never appears at all, in either `designation` or
    `fullName`. Same manual-include fix.
  - **`seki` (Sequoia & Kings Canyon)** — NPS represents these as **one combined API
    record** (`designation: "National Parks"`, plural), but they're officially counted as
    2 separate parks everywhere, including this app's own "X of 63" passport framing. This
    was a real design decision (confirmed with you): `expand_combined_parks()` splits the
    one API record into two synthetic `Park` rows (`seki-sequoia` / `seki-kings`) with a
    made-up park code, sharing the original record's description/coordinates/states, since
    NPS doesn't provide separate ones. The alternative (keep it as one combined entry) would
    have permanently capped the passport at 62/63.
  - Also confirmed **not** part of the 63 despite "National Park" in their names, correctly
    excluded: `npnh` (National Parks of New York Harbor — an administrative grouping of NYC
    sites) and `wotr` (Wolf Trap National Park for the Performing Arts — a concert venue).
  - With all three fixes, filtering + expansion produces exactly 63. The script still warns
    to stderr if the count isn't 63, so a future NPS API change is loud, not silent.
- **No date/notes UI yet.** The API already supports optional `visited_date`/`notes` per
  visit (per spec §2.1/§6), but the Phase 1 grid just toggles visited on/off using today's
  date automatically on click — no date picker or notes field in the UI yet. Keeps the v1
  interaction simple; the backend is already shaped to support richer UI later without an
  API change.
- **Tests use an in-memory SQLite DB** (`aiosqlite`), not the real Postgres, since Docker
  isn't available in this sandbox. Added as a dev dependency; the fixture creates tables via
  `Base.metadata.create_all` rather than running Alembic migrations against SQLite (Alembic
  migration SQL is Postgres-specific in a couple of places — e.g. `SERIAL` — so this avoids
  a second, SQLite-flavored migration path existing only for tests).
- **Health-check endpoints kept, but no longer the homepage.** `/health` and `/health/db`
  from Phase 0 still exist on the backend (useful for ops), but the frontend's home page
  now shows the passport grid instead of the Phase 0 health-check text.

## Full-stack verification

Same Docker constraint as Phase 0: this sandbox can't run Postgres itself, so the following
had to be verified on real hardware instead:

- ✅ **`alembic upgrade head` against real Postgres** — confirmed working (implicitly: the
  ingestion upsert below succeeded, which requires the `parks` table to already exist).
- ✅ **`ingestion/load_parks.py` against a real NPS API key** — confirmed producing exactly
  63 rows and upserting into Postgres with no errors (2026-09-16).
- ✅ **The passport grid loads all 63 parks** in the browser against a real backend + DB —
  confirmed (2026-09-16). Also hit along the way, unrelated to this app: Node 18 (an
  un-pinned terminal) crashes Vite 8/rolldown with a `styleText` `SyntaxError` —
  `util.styleText` needs Node 20.12+. Fixed by running `nvm use` (reads `.nvmrc`) before
  `npm run dev`.
- ⬜ **Marking/unmarking a park visited** (click a card, stamp + counter update, persists
  on refresh) — grid loading is confirmed, this specific interaction isn't yet.

Once the last item's confirmed, all three of spec §7's Phase 1 pieces (park data loaded,
mark visited, see stamps) will be verified against real Postgres + a real NPS API key.
